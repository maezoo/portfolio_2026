01

Context

화면을 만들기 전에,
자료를 다시 이해해야 했습니다.

제공된 자료만으로 바로 화면을 만들기 어려웠고 기존 메뉴도 방문자보다 내부 운영 기준에 가까웠습니다. 요청받은 구성을 그대로 옮기기보다 기존 사이트와 업종을 다시 확인하고, 어떤 정보를 누구에게 먼저 보여줄지 정리하는 과정이 필요했습니다.

02

Problem

정보는 있었지만
찾는 순서가 보이지 않았습니다.

불분명한 우선순위

메뉴와 콘텐츠가 같은 비중으로 나열되어 핵심 정보가 드러나지 않았습니다.

끊기는 모바일 탐색

작은 화면에서 원하는 내용과 문의 동선까지 이동하기 어려웠습니다.

정리되지 않은 자료

기존 자료를 목적과 맥락에 맞게 다시 분류해야 했습니다.

03

My Decision

내부의 분류가 아니라
방문 목적을 기준으로 나눴습니다.

전달받은 메뉴를 그대로 사용하지 않았습니다. 방문자가 먼저 찾을 내용과 사이트에서 이어져야 할 행동을 기준으로 메뉴를 다시 나누고, 중요한 정보와 문의 동선을 앞쪽에 배치했습니다.

기존 사이트·업종 확인→방문 목적별 분류→핵심 정보 우선 배치
04

Design → Build

설계가 실제 환경에서도
같은 의도로 작동하도록.

PC와 모바일 UI를 함께 정리한 뒤 반응형으로 직접 구현하고 CMS에 적용했습니다. 실제 콘텐츠 길이, 관리 방식, 화면 크기 변화까지 고려해 운영자가 내용을 바꾸어도 구조가 무너지지 않도록 구성했습니다.

DESIGN정보 위계와 반응형 UI

화면 크기가 달라져도 핵심 콘텐츠의 우선순위가 유지되도록 설계했습니다.

BUILDPublishing & CMS

직접 구현하고 CMS에 연결해 설계 의도와 실제 결과의 간격을 확인했습니다.

05

After Launch

오픈한 화면을
다시 설계의 근거로 삼았습니다.

실제 콘텐츠가 들어간 뒤 발생한 줄바꿈과 모바일 가독성 문제를 확인해 세부 화면을 보완했습니다. 화면을 넘기는 것으로 끝내지 않고 운영 과정에서 드러난 문제를 다시 디자인에 반영했습니다.

06

Improve

다음 수정이 쉬운 구조도
디자인의 일부였습니다.

반복 수정이 필요한 영역을 컴포넌트 기준으로 정리해 이후 운영의 부담을 줄였습니다. 이 경험을 통해 좋은 화면은 오픈 순간뿐 아니라 실제로 관리되는 동안에도 안정적으로 작동해야 한다는 기준을 갖게 됐습니다.

TAKEAWAY화면을 설계할 때, 구현과 운영에서 생길 일을 함께 생각합니다.
