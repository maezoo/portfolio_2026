01

Context

구현할 수 있는 화면에서
검증할 수 있는 화면으로.

실무를 통해 설계한 화면을 실제 웹으로 구현하고 운영하는 경험은 쌓았지만, 사용자 행동을 근거로 문제를 정의하고 가설을 검증하는 과정은 상대적으로 적게 다뤘습니다. 이를 보완하기 위해 판단 과정이 드러나는 개인 프로젝트를 시작했습니다.

02

Problem

완성도를 높이기 전에
문제가 맞는지 확인해야 했습니다.

가정 중심의 판단

사용자가 어려움을 겪을 것이라는 예상과 실제 행동을 구분할 필요가 있었습니다.

결과 화면 중심

완성된 UI보다 어떤 근거로 변경했는지를 보여주는 과정이 필요했습니다.

늦은 검증

많이 만든 뒤 확인하기보다 핵심 가설을 작은 범위에서 먼저 검증해야 했습니다.

03

My Decision

한 번의 결과물이 아닌
검증의 순서를 설계했습니다.

문제를 먼저 단정하지 않고 관찰한 사실과 해석을 나눠 기록했습니다. 핵심 가설을 정한 뒤 필요한 화면만 프로토타입으로 만들고, 테스트 결과를 다음 화면의 우선순위에 반영했습니다.

Research→Problem→Hypothesis→Prototype→Test
04

Design → Build

핵심 행동을 확인할 만큼만
빠르게 구체화했습니다.

모든 화면을 완성하는 대신 사용자의 핵심 행동과 막히는 지점을 확인할 수 있는 범위로 프로토타입을 설계했습니다. 구현 경험을 활용해 실제 서비스로 이어질 때의 상태와 예외도 함께 고려했습니다.

PROTOTYPE핵심 흐름 우선

가설과 관계없는 장식이나 부가 화면을 줄이고 확인할 행동에 집중했습니다.

FEASIBILITY현실적인 화면 상태

구현과 운영에서 생길 수 있는 상태를 포함해 테스트 결과가 실제 설계로 이어지게 했습니다.

05

After Test

의도한 흐름과 실제 행동의
차이를 기록했습니다.

사용자가 예상과 다른 순서로 정보를 확인하거나 행동을 멈춘 지점을 관찰했습니다. 설명으로 유도하기보다 정보 순서와 행동 단서를 수정하는 방식으로 우선순위를 다시 조정했습니다.

06

Improve

테스트 결과를
다음 화면의 근거로 연결했습니다.

검증 결과를 다음 프로토타입에 반영해 전후의 차이와 판단 이유를 함께 남겼습니다. 이 과정을 통해 구현을 이해하는 강점에 사용자 관찰과 검증을 더해, 더 이른 단계에서 문제를 발견하는 방식을 연습했습니다.

TAKEAWAY빠르게 만드는 능력을, 더 빠르게 확인하고 개선하는 과정으로 확장합니다.
